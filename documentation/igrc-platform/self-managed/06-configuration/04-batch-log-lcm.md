# Batch Log Lifecycle Management

## Overview

The batch service manages log files and execution summaries produced during each data ingestion. After each execution, logs are archived into compressed zip files, and older archives are purged based on configurable retention policies. Execution summaries (`summary.json`) are preserved alongside their archives so the controller can query them at any time.

## File System Layout

```
/var/log/igrcanalytics/
├── batch/
│   ├── 0/                  # Default log folder (used when no ingestion is running)
│   ├── <id>/               # Log folder for batch execution <id>
│   │   └── summary.json    # Execution summary (kept after cleanup)
│   └── current -> batch/<id>   # Symlink pointing to the active/last batch folder
└── archives/
    └── <id>.zip            # Compressed log archive for batch execution <id>
```

## Lifecycle

### 1. Startup Cleanup

When the batch service starts, it runs a cleanup routine that:

1. **Removes orphan batch folders** — any `batch/<id>/` folder whose corresponding `archives/<id>.zip` no longer exists is deleted.
2. **Purges old archives** — applies the retention policy (max count and/or max age) to the `archives/` directory.

### 2. During Execution

When a plan d'exécution is triggered:

1. A new folder `batch/<id>/` is created for the execution logs.
2. The `current` symlink is updated to point to `batch/<id>/`.
3. All log files generated by the Analytics CLI are written into `batch/<id>/`.

### 3. Teardown (Post-Execution)

After each execution completes (success or failure):

1. **Write summary** — the execution summary is written to `batch/<id>/summary.json`.
2. **Create archive** — the entire `batch/<id>/` folder is compressed into `archives/<id>.zip`.
3. **Clean log folder** — all files in `batch/<id>/` are deleted **except** `summary.json`, which is kept so the controller can read it via `GET /batch/summary/:batch-id`.
4. **Purge old archives** — the retention policy is applied, removing archives that exceed the configured max count or max age.
5. **Clean orphan batch folders** — any `batch/<id>/` folder whose `archives/<id>.zip` has been purged is deleted (including its `summary.json`).

This ensures that `batch/<id>/summary.json` and `archives/<id>.zip` always stay in sync: a summary is available if and only if its archive exists.

## Environment Variables

| Variable                | Type     | Default | Disabled value | Description                                                                                                                                                                                    |
| ----------------------- | -------- | ------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LOG_ARCHIVE_MAX_COUNT` | integer  | `0`     | `0`            | Maximum number of log archives to keep. The oldest archives beyond this count are deleted after each execution. Set to `0` to disable count-based purging.                                     |
| `LOG_ARCHIVE_MAX_AGE`   | duration | `0s`    | `0s`           | Maximum age of log archives. Archives older than this duration are deleted. Uses Go duration format (e.g. `168h` for 7 days, `720h` for 30 days). Set to `0s` to disable age-based purging.    |
| `DELETE_LOGS_ZIP`       | boolean  | `true`  | —              | When `true`, compressed log files (`logs_*.zip`) generated by the Analytics CLI inside `batch/<id>/` are deleted before creating the final archive. This avoids archiving redundant zip files. |

## Helm Chart Configuration

The retention policy is configured through `values.yaml` under the `batch.archiveLogs` key:

```yaml
batch:
  archiveLogs:
    # Maximum number of log archives to keep (0 = no count-based purge)
    maxCount: 10
    # Maximum age of log archives (Go duration format, "0s" = no age-based purge)
    maxAge: 168h
```

| Value                        | Type     | Default | Description                                                                                                                               |
| ---------------------------- | -------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `batch.archiveLogs.maxCount` | integer  | `10`    | Maps to `LOG_ARCHIVE_MAX_COUNT`. Set to `0` to disable count-based purging.                                                               |
| `batch.archiveLogs.maxAge`   | duration | `120h`    | Maps to `LOG_ARCHIVE_MAX_AGE`. Set to `0s` to disable age-based purging. Must be a valid Go `time.Duration` string (e.g. `168h`, `720h`). |

These values are injected as environment variables into the `data-ingestion` statefulset (see Environment Variables above for details on each variable).

> **Warning**: the documentation previously used `5d` as an example for the `batch.archiveLogs.maxAge` value, which is incorrect. Use `120h` instead!

### Examples

**Keep the last 20 archives, purge those older than 30 days:**

```yaml
batch:
  archiveLogs:
    maxCount: 20
    maxAge: 720h
```

**Disable all automatic purging (archives accumulate indefinitely):**

```yaml
batch:
  archiveLogs:
    maxCount: 0
    maxAge: "0s"
```

**Count-based only (keep last 5, no age limit):**

```yaml
batch:
  archiveLogs:
    maxCount: 5
    maxAge: "0s"
```

### Disabling Purge Policies

Both variables will typically always be set in the deployment manifest. To explicitly disable a policy:

```yaml
- name: LOG_ARCHIVE_MAX_COUNT
  value: "0" # No count-based purge
- name: LOG_ARCHIVE_MAX_AGE
  value: "0s" # No age-based purge
```

When both are set to their disabled value, no automatic purging occurs and archives accumulate indefinitely.

### Configuration Examples

**Keep the last 10 archives, no age limit:**

```yaml
- name: LOG_ARCHIVE_MAX_COUNT
  value: "10"
- name: LOG_ARCHIVE_MAX_AGE
  value: "0s"
```

**Keep archives for 7 days, no count limit:**

```yaml
- name: LOG_ARCHIVE_MAX_COUNT
  value: "0"
- name: LOG_ARCHIVE_MAX_AGE
  value: "168h"
```

**Keep the last 5 archives or those younger than 30 days (both rules apply):**

```yaml
- name: LOG_ARCHIVE_MAX_COUNT
  value: "5"
- name: LOG_ARCHIVE_MAX_AGE
  value: "720h"
```

When both `LOG_ARCHIVE_MAX_COUNT` and `LOG_ARCHIVE_MAX_AGE` are active, an archive is deleted if it exceeds **either** limit (union of both criteria).

### Important Notes

- **Purged logs are no longer downloadable.** When an archive is deleted by the retention policy, its corresponding execution summary (`summary.json`) is also removed. The controller's log download endpoint (`GET /batch/logs/:batch-id`) will return a `404` for any purged execution. Make sure the retention settings match the window during which users need to access historical logs.
- `LOG_ARCHIVE_MAX_AGE` must be a valid Go `time.Duration` string. Valid examples: `1h`, `24h`, `168h` (7 days), `720h` (30 days). Values like `7d` or `1d` are **not** supported and will be ignored with a warning in the logs.
- The `current` symlink always points to the last executed batch folder. It is not reset after teardown since the folder (with its `summary.json`) is preserved as long as the archive exists.
