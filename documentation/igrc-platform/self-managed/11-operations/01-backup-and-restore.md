# Backup and restore

No backup is configured by default. With the built-in database, enable the CloudNativePG backups of both charts as soon as the platform holds data you need to keep.

> [!note] The database backup and restore procedures of this page apply only to the built-in database (`database.type: internal`). With an external database, backing up and restoring the PostgreSQL server is outside the scope of this documentation: plan it with the DBAs of your organisation. The other items of this page (Git project, installation settings, generated secrets, controller volumes) apply to both modes.

## What to back up

| Item | Where it lives | How to back it up |
| :--- | :------------- | :---------------- |
| Identity Ledger, workflows, audit logs, configuration store, controller data | `shared-db` cluster of each instance (databases `analytics_db` and `shared_db`) | Built-in database: CloudNativePG backups of the `ida-helm` chart. External database: your DBAs |
| Users, roles, realms, identity provider settings | `keycloak-db` cluster of Shared Services | Built-in database: CloudNativePG backups of the `ida-shared-helm` chart. External database: your DBAs |
| Project | Your Git repository | Already versioned outside the cluster |
| Source files uploaded to the controller | `controller` volumes | Keep them at the source, or back up the volumes with your own tool (see [Controller volumes](#controller-volumes)) |
| Installation settings | Your values files, the license and the secrets you created (registry, TLS, object store) | Store them in your configuration management, without plain passwords |
| Secrets generated by the charts | Both namespaces (see below) | Export them with your values files |

### Secrets generated by the charts

At the first installation, the charts generate keys and passwords and store them in Kubernetes secrets. They are kept on upgrades, but a new installation generates new ones. Keep a copy of the following secrets in a safe place: a restore needs them.

- In `<IDA_NAMESPACE>`:
    - `secrets-store-encryption-key` and `secrets-store-encryption-key-v2`: they encrypt the secrets stored in the configuration store (for example the Git credentials). Without them, a restored configuration store cannot be read: the Git synchronisation fails and the portal does not start.
    - `controller-cookie-secret-key`.
    - `keycloak-app-realm-admin-credentials`, only if `global.technicalAdmin.password` is not set in your values: it holds the initial password of the technical administrator.
- In `<SHARED_NAMESPACE>`: `keycloak-master-admin`, `keycloak-db-credentials`, `keycloak-svc-admin-credentials`, `apisix-admin-credentials` and `apisix-etcd-jwt-token`.

```bash
kubectl get secret -n <IDA_NAMESPACE> secrets-store-encryption-key secrets-store-encryption-key-v2 \
  controller-cookie-secret-key keycloak-app-realm-admin-credentials -o yaml > ida-secrets.yaml
kubectl get secret -n <SHARED_NAMESPACE> keycloak-master-admin keycloak-db-credentials \
  keycloak-svc-admin-credentials apisix-admin-credentials apisix-etcd-jwt-token -o yaml > shared-secrets.yaml
```

The other secrets of the namespaces (database accounts, OIDC client secrets, copies of the Shared Services secrets in the instance namespace) are regenerated or copied again at installation: you do not need to save them. These files contain passwords and keys: store them encrypted.

## Enable the database backups

This section applies only to the built-in database.

CloudNativePG backs up the databases with Barman to an object store: Amazon S3 or an S3-compatible store, Azure Blob Storage or Google Cloud Storage. It takes scheduled base backups and archives the write-ahead logs (WAL) continuously, which allows point-in-time restores.

> [!warning] The chart backups use the Barman Cloud support built into CloudNativePG, which CloudNativePG plans to remove in version 1.30.0. Keep the CloudNativePG operator below 1.30 as long as you use these backups.

Add the same kind of block to `ida.values.yaml` and to `shared.values.yaml`, with a different destination path for each:

```yaml
database:
  backup:
    enabled: true
    destinationPath: "<BUCKET_PATH>"
    s3:
      enabled: true
      existingSecret: "<S3_SECRET>"
    retentionPolicy: 30d
    schedule:
      enabled: true
      # six fields, seconds first: every day at 02:00
      expression: "0 0 2 * * *"
    onUpgrade:
      enabled: true
```

- `existingSecret` holds the `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY` keys. On AWS you can use the pod identity instead, with `s3.inheritFromIAMRole: true`. For S3-compatible stores, set `s3.endpointURL` and, if needed, `s3.endpointCA`.
- For Azure, use the `azure` block (`connectionString`, storage account and key, or `inheritFromAzureAD`). For Google Cloud, use the `gcs` block (`applicationCredentials`, `existingSecret` or `gkeEnvironment`).
- `onUpgrade.enabled` takes a backup before each chart upgrade. The backup taken by the upgrade that enables the backups fails with `cannot proceed with the backup as the cluster has no backup section`: this is expected, the next ones succeed.
- `data.compression`, `wal.compression` and the `encryption` settings control how backups are stored.
- The backups of a database cluster are stored under `<BUCKET_PATH>/<CLUSTER_NAME>/`, in `base` (base backups) and `wals` (write-ahead logs).

Check the backups with:

```bash
kubectl get backups.postgresql.cnpg.io,scheduledbackups.postgresql.cnpg.io -n <IDA_NAMESPACE>
kubectl get backups.postgresql.cnpg.io,scheduledbackups.postgresql.cnpg.io -n <SHARED_NAMESPACE>
```

### Take a backup on demand

To take a base backup without waiting for the schedule, for example right after enabling the backups or after a restore, create a `Backup` resource:

```bash
kubectl apply -f - <<EOF
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  name: shared-db-manual-1
  namespace: <IDA_NAMESPACE>
spec:
  cluster:
    name: shared-db
  method: barmanObjectStore
EOF
```

For Shared Services, use the cluster `keycloak-db` in `<SHARED_NAMESPACE>`. The backup is complete when `kubectl get backup -n <namespace> <name>` shows the phase `completed`.

## Controller volumes

The source files uploaded to the controller are stored on its volumes, in both database modes. The charts do not back them up. Either keep the files at their source so that you can upload them again, or back up the volumes of `<IDA_NAMESPACE>` with the tool your organisation uses for Kubernetes, for example a [Velero](https://velero.io/) server you operate.

## Restore

This section applies only to the built-in database. With an external database, restore the databases with your DBAs, then reinstall the charts with the same values and the generated secrets you saved.

A restore creates a new database cluster from a backup. Use it on a new installation (new cluster or new namespaces), or after removing the releases and their volumes.

The Keycloak database holds the realms of all the instances: restore Shared Services and the instances from backups taken at about the same time, so that users and roles match the data. Restoring Keycloak brings all the instances of the cluster back to the time of the backup.

> [!warning] Uninstalling an instance with `helm uninstall` deletes its Keycloak realm. To restore a single instance while keeping Shared Services as they are, remove it with `helm uninstall --no-hooks`, so that its realm is kept, or restore Shared Services too.

### 1. Recreate the namespaces and the secrets

1. Create the namespaces and the registry secret, as for the [installation](../03-installation.md).
2. Create the secret of the object store (`<S3_SECRET>`, keys `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY`) in both namespaces.
3. Recreate the generated secrets you saved, **before** installing the charts. Remove the `metadata.resourceVersion`, `uid`, `creationTimestamp` and `managedFields` fields of the exported files, then create them with the `helm` field manager:

    ```bash
    kubectl create --field-manager=helm -f shared-secrets.yaml
    kubectl create --field-manager=helm -f ida-secrets.yaml
    ```

    With another field manager (a plain `kubectl create` or `kubectl apply`), the `helm install` fails with `conflict occurred while applying object … conflicts with "kubectl-create"`. If this happened, run the `helm upgrade` of the release again with `--force-conflicts`: the saved values are kept.

### 2. Restore Shared Services, then each instance

Restore Shared Services first and wait until Keycloak is ready, then restore each instance. For each release:

1. Install the chart with the same values, with two changes:
    - `database.backup.destinationPath` points to a **new, empty** path: the restored cluster cannot write its backups where it restores from;
    - a `recovery` block points to the path of the backup to restore:

    ```yaml
    database:
      backup:
        destinationPath: "<NEW_BUCKET_PATH>"
      recovery:
        enabled: true
        # name of the backed-up cluster: keycloak-db (ida-shared-helm) or shared-db (ida-helm)
        serverName: "shared-db"
        externalCluster:
          name: backup-source
          barmanObjectStore:
            destinationPath: "<BUCKET_PATH>"
            s3:
              enabled: true
              existingSecret: "<S3_SECRET>"
              # S3-compatible stores only
              endpointURL: "<S3_ENDPOINT_URL>"
        # optional: restore to a point in time instead of the latest state
        recoveryTarget:
          targetTime: ""
    ```

    `serverName` is required: it is the name under which the backed-up cluster stored its backups in the object store. If you keep the old destination path, the recovery fails with `WAL archive check failed for server <CLUSTER_NAME>: Expected empty archive`.

2. Wait until the database cluster is healthy and the pods are running. For an instance, log in to the portal and check the data.
3. Remove the `recovery` block, keep `backup` enabled on the new path, and run `helm upgrade` again.
4. [Take a base backup on demand](#take-a-backup-on-demand). Until the first base backup, the new path only holds write-ahead logs and a restore from it fails with `no target backup found`.

> [!caution] Test the restore procedure on a non-production cluster before you rely on it.
