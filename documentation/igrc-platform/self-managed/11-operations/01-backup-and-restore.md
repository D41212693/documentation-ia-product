# Backup and restore

Backups are not configured by default. If you use the built-in database, enable CloudNativePG backups for both charts as soon as the platform contains data you need to retain.

> [!note] The database backup and restore procedures on this page apply only to the built-in database (`database.type: internal`). If you use an external database, work with your organisation's database administrators (DBAs) to plan PostgreSQL backups and restores. The guidance for the Git project, installation settings, generated secrets, and controller volumes applies to both database modes.

## What to back up

| Item | Location | Backup method |
| :--- | :------- | :------------ |
| Identity Ledger, workflows, audit logs, configuration store, and controller data | The `shared-db` cluster of each instance (`analytics_db` and `shared_db` databases) | Built-in database: CloudNativePG backups configured through the `ida-helm` chart. External database: managed by your DBAs. |
| Users, roles, realms, and identity provider settings | The `keycloak-db` cluster in Shared Services | Built-in database: CloudNativePG backups configured through the `ida-shared-helm` chart. External database: managed by your DBAs. |
| Project | Your Git repository | Already version-controlled outside the cluster. |
| Source files uploaded to the controller | Controller volumes | Retain the original files or back up the volumes with your own tool. See [Controller volumes](#controller-volumes). |
| Installation settings | Your values files, license, and any Secrets and ConfigMaps you created, including registry, TLS, and object store credentials, and the CA ConfigMap for [LDAPS or StartTLS](../06-configuration/02-authentication-configuration.md#ldap-over-ssl-and-starttls), if applicable | Store these items in your configuration management system. Do not store passwords in plain text. |
| Secrets generated by the charts | Both namespaces; see [Secrets generated by the charts](#secrets-generated-by-the-charts) | Export the secrets and store them securely with your values files. |

### Secrets generated by the charts

During the initial installation, the charts generate keys and passwords and store them in Kubernetes Secrets. These values persist across upgrades, but a new installation generates new values. Save a secure copy of the following secrets, which are required for a restore.

In `<IDA_NAMESPACE>`:

- `secrets-store-encryption-key` and `secrets-store-encryption-key-v2`: Encrypt secrets in the configuration store, such as Git credentials. Without these keys, the restored configuration store cannot be read, Git synchronisation fails, and the portal does not start.
- `controller-cookie-secret-key`.
- `keycloak-app-realm-admin-credentials`: Contains the initial technical administrator password. Back up this secret only if `global.technicalAdmin.password` is not set in your values files.

In `<SHARED_NAMESPACE>`:

- `keycloak-master-admin`
- `keycloak-db-credentials`
- `keycloak-svc-admin-credentials`
- `apisix-admin-credentials`
- `apisix-etcd-jwt-token`

Export the secrets with the following commands. Omit `keycloak-app-realm-admin-credentials` if `global.technicalAdmin.password` is set in your values files.

```
kubectl get secret -n <IDA_NAMESPACE> secrets-store-encryption-key secrets-store-encryption-key-v2 \
  controller-cookie-secret-key keycloak-app-realm-admin-credentials -o yaml > ida-secrets.yaml
kubectl get secret -n <SHARED_NAMESPACE> keycloak-master-admin keycloak-db-credentials \
  keycloak-svc-admin-credentials apisix-admin-credentials apisix-etcd-jwt-token -o yaml > shared-secrets.yaml
```

You do not need to export the other secrets in these namespaces, such as database account credentials, OIDC client secrets, or copies of Shared Services secrets in the instance namespace. They are regenerated or copied during installation.

The exported files contain passwords and encryption keys. Store them encrypted.

## Enable database backups

This section applies only to the built-in database.

CloudNativePG uses Barman to back up databases to Amazon S3, an S3-compatible object store, Azure Blob Storage, or Google Cloud Storage. It creates scheduled base backups and continuously archives write-ahead logs (WAL), enabling point-in-time recovery.

> [!warning]
> The charts use CloudNativePG's built-in Barman Cloud support, which is scheduled for removal in CloudNativePG 1.31.0. Keep the CloudNativePG operator below version 1.31 while using this backup configuration.

Add a configuration block like the following to both `ida.values.yaml` and `shared.values.yaml`. Use a different destination path for each chart.

```
database:
  backup:
    enabled: true
    destinationPath: "<BUCKET_PATH>"
    s3:
      enabled: true
      existingSecret: "<S3_SECRET>"
    retentionPolicy: 30d
    schedule:
      enabled: true
      # Six fields, starting with seconds: daily at 02:00
      expression: "0 0 2 * * *"
    onUpgrade:
      enabled: true
```

Configure the backup settings as follows:

- `existingSecret`: References a secret containing the `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY` keys. On AWS, you can use pod identity instead by setting `s3.inheritFromIAMRole: true`. For S3-compatible stores, also set `s3.endpointURL` and, if required, `s3.endpointCA`.
- Storage provider: For Azure, use the `azure` block with a `connectionString`, a storage account and key, or `inheritFromAzureAD`. For Google Cloud, use the `gcs` block with `applicationCredentials`, `existingSecret`, or `gkeEnvironment`.
- `onUpgrade.enabled`: Creates a backup before each chart upgrade. During the upgrade that first enables backups, this backup fails with `cannot proceed with the backup as the cluster has no backup section`. This initial failure is expected; subsequent upgrade backups succeed.
- `data.compression`, `wal.compression`, and `encryption`: Control backup compression and encryption.

Backups are stored under `<BUCKET_PATH>/<CLUSTER_NAME>/`. The `base` directory contains base backups, and the `wals` directory contains write-ahead logs.

Check the backups and schedules in both namespaces:

```
kubectl get backups.postgresql.cnpg.io,scheduledbackups.postgresql.cnpg.io -n <IDA_NAMESPACE>
kubectl get backups.postgresql.cnpg.io,scheduledbackups.postgresql.cnpg.io -n <SHARED_NAMESPACE>
```

### Take a backup on demand

To create a base backup without waiting for the next scheduled backup, create a `Backup` resource. For example, run an on-demand backup immediately after enabling backups or completing a restore.

```
kubectl apply -f - <<EOF
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  name: shared-db-manual-1
  namespace: <IDA_NAMESPACE>
spec:
  cluster:
    name: shared-db
  method: barmanObjectStore
EOF
```

For Shared Services, specify the `keycloak-db` cluster in `<SHARED_NAMESPACE>`.

The backup is complete when the following command shows the phase as `completed`:

```
kubectl get backup -n <namespace> <name>
```

## Controller volumes

In both database modes, source files uploaded to the controller are stored on its volumes. The charts do not back up these volumes.

Retain the original files so that you can upload them again, or back up the volumes in `<IDA_NAMESPACE>` with your organisation's Kubernetes backup tool. For example, you can use a self-managed [Velero](https://velero.io/) installation to back up Kubernetes resources and persistent volumes. [velero](https://velero.io/)

## Restore

This section applies only to the built-in database. If you use an external database, work with your DBAs to restore the databases, then reinstall the charts using the same values files and the generated secrets you saved.

A restore creates a new database cluster from a backup. Restore to a new installation, using a new Kubernetes cluster or new namespaces, or remove the existing releases and their volumes before restoring.

The Keycloak database contains the realms for all instances. Restore Shared Services and the instances from backups taken at approximately the same time to keep users and roles consistent with the instance data. Restoring Keycloak returns the identity settings for all instances in the cluster to their state at the time of the backup.

> [!warning]
> Running `helm uninstall` for an instance deletes its Keycloak realm. To restore a single instance without restoring Shared Services, use `helm uninstall --no-hooks` to preserve the realm. Otherwise, restore Shared Services as well.

### 1. Recreate the namespaces and secrets

1. Follow the [installation instructions](../03-installation.md) to create the namespaces, registry secret, and any other Secrets or ConfigMaps referenced in your values files. Include `<TLS_SECRET>` if the ingress serves TLS, and the `ldap-ca` ConfigMap if you use LDAPS or StartTLS.

2. Create the object store secret in both namespaces. For the S3 configuration shown above, create `<S3_SECRET>` with the `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY` keys.

3. Restore the generated secrets before installing the charts. Remove the `resourceVersion`, `uid`, and `creationTimestamp` fields from the exported files, then create the secrets using the `helm` field manager:

    ```
    grep -v -E '^\s+(resourceVersion|uid|creationTimestamp):' shared-secrets.yaml > shared-secrets.clean.yaml
    grep -v -E '^\s+(resourceVersion|uid|creationTimestamp):' ida-secrets.yaml > ida-secrets.clean.yaml
    kubectl create --field-manager=helm -f shared-secrets.clean.yaml
    kubectl create --field-manager=helm -f ida-secrets.clean.yaml
    ```

    Using a different field manager, such as the default for `kubectl create` or `kubectl apply`, causes `helm install` to fail with a conflict such as `conflict occurred while applying object … conflicts with "kubectl-create"`. If this occurs, rerun `helm upgrade` for the release with `--force-conflicts`. The saved secret values are preserved.

### 2. Restore Shared Services, then each instance

Restore Shared Services first and wait until Keycloak is ready. Then restore each instance.

For each release:

1. Install the chart using the original values files, with the following changes:

    - Set `database.backup.destinationPath` to a new, empty path. The restored cluster cannot write backups to the path it is restoring from.
    - Add a `recovery` block that points to the original backup path.

    ```
    database:
      backup:
        destinationPath: "<NEW_BUCKET_PATH>"
      recovery:
        enabled: true
        # Backed-up cluster: keycloak-db for ida-shared-helm, shared-db for ida-helm
        serverName: "shared-db"
        externalCluster:
          name: backup-source
          barmanObjectStore:
            destinationPath: "<BUCKET_PATH>"
            s3:
              enabled: true
              existingSecret: "<S3_SECRET>"
              # S3-compatible stores only
              endpointURL: "<S3_ENDPOINT_URL>"
        # Optional: restore to a specific time instead of the latest available state
        recoveryTarget:
          targetTime: ""
    ```

    Set `serverName` to the name under which the original cluster stored its backups: `keycloak-db` for Shared Services or `shared-db` for an instance. This setting is required.

    If you reuse the original backup destination for new backups, recovery fails with `WAL archive check failed for server <CLUSTER_NAME>: Expected empty archive`.

2. Wait until the database cluster is healthy and the pods are running. For an instance, log in to the portal and verify the restored data.

3. Remove the `recovery` block, keep backups enabled with the new destination path, and run `helm upgrade` again.

4. [Take a base backup on demand](#take-a-backup-on-demand). Until the first base backup completes, the new destination contains only write-ahead logs. Restoring from that destination fails with `no target backup found`.

> [!caution]
> Test the restore procedure in a non-production cluster before relying on it.
